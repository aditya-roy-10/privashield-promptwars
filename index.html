The problem

One careless paste can expose everyone in the file.

Every day, logs, resumes, support tickets and clinical notes get forwarded, screenshotted and uploaded — carrying email addresses, phone numbers, Aadhaar and PAN numbers, card details and IP addresses with them. Once a document is shared, that exposure can't be taken back.

How PII leaks

Identifiers hide inside ordinary text — a signature block, a KYC export row, a debug log line. Manual find-and-replace misses repeats, formatting variants and values nobody noticed were there, and uploading the file to an online tool creates a second copy of the very data you're trying to protect.

How PRIVASHIELD fixes it

PRIVASHIELD scans the document locally, classifies every identifier with real validation evidence — Luhn for cards, Verhoeff for Aadhaar — and redacts it in your choice of three modes. Borderline matches are flagged for your review, never silently trusted or silently dropped, and nothing is uploaded anywhere in the process.

Features

A complete sanitization toolkit, in one tab.

Everything below is implemented and running in the workspace today — open the app and try each one on the built-in sample.

Intelligent PII detection

Six identifier categories — email, phone, IPv4/IPv6, PAN, Aadhaar and credit cards — with context-aware classification that separates real identifiers from order numbers, timestamps and invoice references. Uncertain matches surface as review candidates instead of disappearing.

Luhn & checksum validation

Cards must pass the Luhn algorithm; Aadhaar numbers are verified with the Verhoeff checksum; PAN holder codes and IPv4 octets are structure-checked. A checksum pass means mathematical consistency — the UI never claims it proves an identity is genuine.

Three redaction modes

Full Mask replaces values with [REDACTED]. Partial Mask keeps limited verification context, like a card's last four digits. Pseudonymization swaps in consistent aliases. Switch modes instantly — the output re-renders from the same scan.

Consistent pseudonymization

The same identifier always becomes the same alias — EMAIL_001, PHONE_001, CARD_001 — even across formatting variants and CSV rows, so relationships in the data survive. The mapping lives only in tab memory and is never exported.

Live side-by-side comparison

Original and sanitized text side by side with color-coded highlighting, line numbers and synchronized scrolling. Click any finding in the inspector to jump straight to its occurrence in the document.

Privacy analytics

A live dashboard computed from the current scan: total occurrences, unique identifiers, redaction coverage, an entity-distribution donut, and a transparent privacy exposure score — estimated exposure before sanitization versus residual after, using published per-category sensitivity weights. Every number traces back to an actual detection — nothing is decorative.

Leak Guard

After sanitization, a second detection pass re-scans the output with the same pattern/checksum engine (so it shares the primary scan's blind spots). Anything still matching a supported pattern — a value you excluded during review, a category switched off, a Keep override — is listed with the reason it survived, and downloads pause with a warning until you resolve it or explicitly export anyway. A clear pass means no supported patterns remain, never a guarantee of complete anonymization.

Sanitization audit reports

Download a human-readable or JSON audit report for every sanitization: timestamp, document type and size, per-category counts, validation results, redaction mode, redacted and excluded counts, Leak Guard's remaining matches, exposure before and after, and an optional SHA-256 hash of the sanitized output — generated with the browser's Web Crypto API. Reports contain counts only: no PII, no raw text, no filenames, no pseudonym mapping — and they are labelled an application-generated report, not a compliance certificate.

Offline processing

The page makes zero runtime network requests — the engine, the CSV parser and every asset are already on the page. Load it once and it keeps working with the network unplugged, and no document is ever stored between sessions.

How it works

From raw document to safe-to-share in three steps.

STEP 01

Add your document

Upload a TXT or CSV file — drag and drop works too — or paste raw text straight into the workspace. CSV files keep their structure: headers, rows, columns and quoted fields are preserved.

STEP 02

Detect, review, sanitize

The engine detects and validates identifiers as you type. Review each finding in the inspector — approve a candidate, exclude a false alarm, or override its redaction mode — then pick Full Mask, Partial Mask or Pseudonymization.

STEP 03

Verify & download

Compare the sanitized output against the original, check the coverage meter and the remaining-matches count, then download the cleaned TXT or CSV — or copy it — with one click.

How PRIVASHIELD handles your data

Every document you paste or load is processed entirely inside this browser tab. Detection, validation, redaction and export all run in local memory — there is no backend to send anything to.

  • No transmission: no server calls, no external AI APIs, no analytics or telemetry. This page makes zero runtime network requests.
  • No storage: nothing is written to localStorage, cookies, IndexedDB or disk. Closing the tab — or pressing Clear session — destroys the document, review decisions and pseudonym mapping.
  • Pseudonym mapping stays here: the original-to-alias mapping lives only in tab memory, is never shown as a table and is never included in downloads.
  • Validation ≠ verification: a Luhn or Verhoeff pass means a value is mathematically consistent — never that an identifier is genuine, issued or owned.
  • Partial masks & pseudonyms are still sensitive: retained fragments and linkable aliases can re-identify people; handle exports accordingly.

How this score is calculated — and what it is not

Each detected occurrence contributes its category's sensitivity weight (editable above; the defaults are illustrative). The weighted total is mapped onto 0–100 with a saturating curve — score = 100 × (1 − 1 ÷ (1 + total ÷ 50)) — so a single Aadhaar scores 17, and the score approaches 100 as exposure accumulates instead of growing without bound. Residual exposure counts every supported pattern Leak Guard still finds in the output at full weight, plus 40% of the weight of each partially masked value (its retained fragments still identify). The same inputs always produce the same score — it is deterministic and computed only from this document's detections. It is an estimated exposure heuristic, not a regulatory compliance score, and a residual score of 0 means only no residual exposure measured by the supported scoring rules — never a guarantee of complete anonymization, since names, addresses and obfuscated identifiers are outside its scope.

Known limitations (honest list)
  • Leak Guard re-scans for the six supported patterns only — a clear result means no supported patterns remain, not that a document is guaranteed anonymous; the exposure score inherits the same scope.
  • Exposure weights are illustrative defaults; the score is a triage heuristic for comparing before/after on the same document, not a risk measurement comparable across organisations.
  • For CSV input, Leak Guard scans the document-level sanitized text; the per-cell export applies the same keep/redact decisions by value, so coverage matches, but cell boundaries are not re-scanned separately.
  • SHA-256 report hashes need Web Crypto (secure context); where unavailable the report records the hash as null instead of inventing one.
  • Partial-mask policies are fixed per type — no per-type policy editor (e.g. choosing how many digits to reveal).
  • Pseudonymized output is still personal data, not anonymous data — aliases preserve linkability by design.
  • Typing a wholly new document into the textarea does not reset the pseudonym store; load via file/sample or Clear session to restart aliasing from 001.
  • Detection can still miss obfuscated PII (e.g. “user at gmail dot com”) and free-text names/addresses, which need NER.
  • Checksum/format validation is not identity verification — a Luhn/Verhoeff pass never means an identifier is genuine.
  • Phone support covers Indian + common intl. shapes; exotic national formats may be missed or need review.
  • Review decisions are keyed by type + offsets — editing text before a detection shifts its offsets and that decision stops applying.
  • Context is keyword-based (±80 chars); negation or keywords in other languages are not understood.
